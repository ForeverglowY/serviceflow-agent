# Day26：3～5分钟演示讲稿与排练

状态：已准备脚本，尚未录制视频。不将准备稿视为已录制交付。

## 开场（0:00～0:25）

口述：

> 这是ServiceFlow，一个使用模拟数据的电商客服与售后申请Agent。
> 我用它演示模型如何结合政策资料回答、通过多轮对话收集申请，并在用户明确确认后受控登记工单。
> 模型负责理解，程序负责规则和数据库写入；登记不代表退换货获批。

打开容器版 http://127.0.0.1:8001/docs 的POST /agent/chat，不录制.env、密钥、个人邮件或其他真实隐私。
全程保持Docker服务运行，不依赖本机Uvicorn。真实模型会有等待且产生费用；若剪辑等待，需要标明，不将剪辑后时长当作响应耗时。

## 场景一：正常售后政策咨询（0:25～1:10）

```json
{"message":"已拆封的入耳式耳机左耳无声，可以退货吗？"}
```

预期：回答检测前提并带政策引用，不承诺获批。

口述：

> 这个请求进入RAG分支，问题先向量化，再检索有效政策。模型只拿到Top-K资料，不是每次读取整个知识库。
> 程序校验引用编号并拼接来源；引用合法仍不保证回答语义绝对正确，因此我另外做了回答复核。

展示回答和引用即可，不展开全部检索日志。本场景的thread_id不带入下一场景，避免把独立咨询与申请混为一谈。

## 场景二：缺少信息，跨轮收集（1:10～2:20）

先新开会话：

```json
{"message":"帮订单20260721001创建售后工单"}
```

复制本次返回的thread_id，后续使用同一个真实编号：

```json
{"message":"左耳没有声音","thread_id":"替换为本场景返回的编号"}
```

```json
{"message":"换货","thread_id":"替换为同一个编号"}
```

预期：依次追问故障及处理方式；保留订单号；完整后给摘要及预评估，提示确认；还没有创建工单。

口述：

> 模型每次只提取当前消息明确提供的信息，程序把非空字段合并进已有状态。
> LangGraph的checkpoint保存进度，所以“左耳没有声音”和“换货”能接着上一轮处理。
> 活跃申请优先进入工单子图，不会每轮都把短回复重新当成独立问题分类。

## 场景三：明确确认，登记人工核验（2:20～3:40）

这是场景二的延续，不新建thread_id。只有摘要正确且确实准备写入演示库时才提交：

```json
{"message":"确认","thread_id":"替换为场景二的同一个编号"}
```

此请求会创建真实的本地演示工单及确认记录，并在需要时登记人工待处理任务。
复制返回的ticket_id，通过GET /tickets/{ticket_id}核对订单及description。

口述：

> 当前是疑似质量问题、尚无检测结果，程序不会批准换货，只登记申请和人工核验任务。
> 用户确认快照与工单同事务写入，提交标识和数据库唯一约束避免同一次申请重复创建。
> 人工登记是另一个事务，失败通过独立resume入口恢复，不在普通聊天里忽略用户新消息自动重试。

不要连续重复“确认”来演示幂等，也不要录制时故意中断数据库；相应能力通过独立集成测试证明。

## 收尾（3:40～4:20）

重点展示已知限制，而不是宣称100%准确率、所有攻击都能防住或生产高并发能力。

## 可选备用：明确拒绝，与人工核验区分

若面试追问“是不是所有申请都转人工”，新开独立会话：

```json
{"message":"帮订单20260721002创建售后工单，键盘坏了，我想换货"}
```

订单需仍未支付，预期明确拒绝，不引导确认。
reject表示当前条件不允许提交，need_manual_review表示尚不能自动确认条件、允许登记待核验申请。两者不能说成同一流程。
