# ServiceFlow 演示说明

3～5分钟面试演示使用 [排练讲稿](demo-rehearsal.md)，下文保留更详细的独立验收场景。

## 演示前准备

按 README 完成依赖安装、数据库迁移、测试数据初始化和政策向量索引；不要为了演示删除已有数据库。
容器方式运行 `docker compose --profile app up -d`，打开 http://127.0.0.1:8001/docs；本机Python方式按README启动后访问8000。二者不要混淆。
使用模拟数据，不输入真实客户隐私。真实模型调用会产生 API 费用。

以下三个场景是独立演示：每个场景第一条消息不传 thread_id，避免活跃工单收集影响其他场景。
预期描述是验收条件，不要求模型逐字输出相同文案。

## 场景一：订单与物流（约2分钟）

请求 `POST /agent/chat`：

```json
{"message":"帮我查询订单20260721001，并看看它的物流到哪里了"}
```

验收：订单和物流数据来自工具，不能编造送达日期或把“待处理”改写为“待发货”。
订单记录无物流单号、物流表有单号时，应按各工具返回结果说明，不得仅因 null 判定未发货。

复制响应头 X-Trace-ID，运行报告命令，检查工具步骤和模型调用。模型选择存在变化，不硬编码调用次数作为验收条件。

讲解：外层意图识别 → tools 分支 → 模型选择工具 → 参数校验及数据库查询 → tool 消息回传 → 最终回答。
源码入口：`serviceflow/agent/workflow.py`、`serviceflow/agent/graph.py`、`serviceflow/agent/tools.py`。

## 场景二：政策 RAG（约2分钟）

仍请求 `POST /agent/chat`，不沿用场景一会话：

```json
{"message":"入耳式耳机已经拆封，但是左耳没有声音，可以退货吗？"}
```

验收：回答质量检测及非人为故障核验条件，区分无理由退货与质量问题，不承诺已经获批；来源编号必须来自检索结果。
若意图识别进入申请分支而非政策分支，先看实际日志确认路由，不将追问当作 RAG 验收通过。

另开会话询问“你们公司食堂几点开门？”。系统应安全回退或表示资料不足，不能编造时间；该问题不保证进入 RAG 分支。

讲解：查询向量 → 生效政策过滤和 pgvector 检索 → 带编号上下文 → 模型结构化回答 → 引用白名单校验 → 程序拼接来源。
源码入口：`serviceflow/rag/database_retriever.py`、`serviceflow/rag/service.py`。

## 场景三：多轮申请、确认与工单登记（约4分钟）

第一轮 `POST /agent/chat`：

```json
{"message":"帮订单20260721001创建售后工单"}
```

复制响应 body 中的 thread_id。后续消息必须填真实的同一编号，下面的占位符不是有效演示编号。

第二轮：

```json
{"message":"左耳没有声音","thread_id":"替换为第一轮返回的thread_id"}
```

第三轮：

```json
{"message":"换货","thread_id":"替换为第一轮返回的thread_id"}
```

验收：分轮补全订单号、问题描述、处理方式；已有字段不丢失，申请齐全后进行规则预评估，展示摘要并引导确认。
此时只是申请预览，尚未创建工单，不应承诺换货获批。

确认（此操作会真实写入本地演示数据库）：

```json
{"message":"确认","thread_id":"替换为第一轮返回的thread_id"}
```

验收：返回真实工单号；疑似质量问题需要人工核验时，登记人工待处理任务，不能声称审核通过。
用 `GET /tickets/{ticket_id}` 查询返回的工单号，核对订单和描述。

讲解：活跃申请优先进入工单子图 → 提取及合并 → 规则预评估 → 等待明确确认 → submission_id 防重 → 同事务保存工单与确认 → 人工任务登记。
源码入口：`serviceflow/agent/ticket_collection.py`、`serviceflow/ticket/service.py`、`serviceflow/ticket/review.py`。

重复发送“确认”不是可靠的幂等演示方法：完成申请后的新聊天有新的业务语义。
幂等与失败恢复用专用集成测试证明，不在普通聊天入口自动恢复，也不故意损坏演示数据库：

```bash
uv run python -m pytest tests/test_ticket_idempotency_integration.py tests/test_ticket_checkpoint_integration.py -q
```

这些测试模拟模型输出，使用真实 PostgreSQL 验证重复提交、并发冲突和断开连接后恢复；不等于真实模型端到端验证。

## 演示结论与边界

这是个人应用工程项目，非生产上线系统。三个业务分支互补，不意味着每次申请都会执行 RAG。
SSE 当前是独立文本生成 Demo，不是整个工作流的流式化。
尚无真实身份认证、会话所有权校验、人工审核页面和退款支付执行；没有业务用户量及收益指标。
日志报告是单服务请求关联，不是完整分布式追踪。不要公开上传 .env 或原始服务器日志。
