# ServiceFlow 项目简历描述（第一版）

## 可放入简历的版本

**ServiceFlow｜智能客服与售后工单 Agent（个人项目）**

技术栈：Python、FastAPI、LangGraph、DeepSeek、Pydantic、SQLAlchemy、PostgreSQL、pgvector、Sentence Transformers。

- 构建电商客服工作流，支持订单与物流工具查询、售后政策 RAG、多轮申请收集及确认后工单登记；使用模拟业务数据与政策。
- 使用 LangGraph 实现外层意图路由、内层工具调用循环和工单状态子图，通过 PostgreSQL Checkpointer 持久化会话；结合工具白名单、参数校验和最大调用轮数约束执行范围。
- 实现政策章节切分、内容哈希增量索引、pgvector 语义检索，以及生效日期与状态过滤；对模型结构化引用做白名单校验，由程序生成真实来源，降低虚构引用风险。
- 将模型信息提取与确定性业务规则分离，实现售后预评估、用户确认快照、提交标识唯一约束防重、工单与确认同事务写入，以及显式失败恢复和人工待处理任务登记。
- 实现 SSE 文本生成演示及请求级日志追踪，记录工具耗时、模型用量与执行结果，支持按 trace_id 生成调用链报告；通过单元测试及 PostgreSQL 集成测试验证关键路径。

## 60秒口述版本

我做了一个电商客服与售后工单 Agent，重点是把模型能力接入可控的后端业务流程，而不只是聊天。
查询类问题由模型选择受控工具获取数据库事实；政策问题通过向量检索和引用校验回答；
售后申请用状态图收集信息、执行规则、让用户确认后再创建工单。
我用 PostgreSQL 保存会话和业务数据，处理重复提交、失败恢复和确认审计，并加了流式演示与调用链日志。
这是使用模拟数据的个人项目，没有宣称上线收益；我可以结合代码和测试解释模型与程序各自的责任边界。

## 面试前必须能解释的内容

1. 第一次模型调用为什么返回工具请求，第二次为什么要携带工具结果？
2. thread_id、trace_id、submission_id 分别解决什么问题？
3. checkpoint 如何支持跨轮对话和节点失败后恢复？为什么恢复与聊天分开？
4. 唯一约束如何处理并发重复提交？为什么不能只“先查再插入”？
5. RAG 的 Top-K、过滤、引用检查分别约束什么，为什么引用合法不代表回答必然正确？
6. 什么动作必须由程序或人工判断，不能只依赖提示词？
7. 流式响应已经开始后，失败为什么通常通过 SSE error 事件反馈？
8. 为什么已经有 checkpoint，创建工单时仍然需要 `submission_id` 和数据库唯一约束？

   checkpoint负责保存流程状态，但业务写入和checkpoint保存的不是同一个原子事务。可能出现工单已经提交，而流程完成状态还没保存的情况，恢复后节点会重复执行。因此我为每次申请保存稳定的submission_id，重试时返回原工单，并用数据库唯一约束处理并发重复提交。

   checkpoint：恢复进度

   submission_id：识别同一次提交

   唯一约束：阻止数据库出现重复结果

## 不要写入简历的说法

- 不写“企业级生产上线”“服务数万用户”或没有实测依据的性能提升百分比。
- 不把关键词与向量 RRF 实验描述为已全面接入生产路径；不把文本流 Demo 描述为全工作流流式化。
- 不写“彻底防止幻觉或提示词注入”“所有操作 exactly-once”“自动批准退款”。
- 不用一组小规模 Hit@K 的100%结果代表普遍正确率；不把测试数量当作业务效果。
